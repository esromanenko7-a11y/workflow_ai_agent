# Выбор embedding-модели для RAG-ассистента
## Предметная область

Ассистент предназначен для работы с русскоязычными документами и результатами проверок пакетов данных.

Основные сценарии поиска:

- объяснение критических ошибок;
- поиск требований к составу пакета;
- поиск рекомендаций по исправлению ошибок;
- определение возможности передать пакет дальше;
- поиск правил по статусам проверок.

Поиск является **асимметричным**:

- пользователь формулирует короткий вопрос;
- система находит наиболее релевантный фрагмент документа.

---

# Выбранная модель

`intfloat/multilingual-e5-small`

---

# Обоснование выбора модели

## Поддержка русского языка

Модель поддерживает русский язык и хорошо подходит для мультиязычного семантического поиска.

Это важно, поскольку вопросы пользователей и документы проекта преимущественно русскоязычные.

---

## Оптимизация под Retrieval

Модель относится к семейству **E5** и специально разработана для сценария **query → document** (asymmetric retrieval).

Для достижения максимального качества используются специальные префиксы.

Для пользовательского запроса:

```text
query:
```

Для документов:

```text
passage:
```

Поэтому в проекте реализованы отдельные методы:

```python
embed_query(text)
embed_documents(texts)
```

а не одна универсальная функция.

---

## Размерность эмбеддингов

Размер одного embedding-вектора:

```text
384
```

Небольшая размерность позволяет:

- уменьшить объём хранения;
- сократить потребление памяти;
- уменьшить размер будущего векторного индекса;
- ускорить поиск ближайших соседей.

---

## Локальный запуск

Модель запускается локально с использованием библиотеки `sentence-transformers`.

Преимущества такого подхода:

- отсутствует стоимость использования API;
- документы не передаются внешнему провайдеру;
- отсутствуют сетевые задержки;
- отсутствуют ограничения по количеству запросов;
- можно использовать локальный дисковый кеш эмбеддингов.

Ограничения:

- требуется загрузка модели при первом запуске;
- скорость зависит от производительности CPU или GPU;
- модель занимает место на диске.

---

# Результаты mini-benchmark

Для проверки качества был подготовлен набор из 6 тестовых сценариев.

Каждый сценарий содержит:

- пользовательский запрос;
- релевантный фрагмент документа;
- нерелевантный фрагмент документа.

Результат проверки:

```text
Passed: 6/6
Accuracy: 100.00%
```

Во всех тестовых сценариях релевантный документ получил более высокий cosine similarity, чем нерелевантный.

Следует отметить, что данный результат относится **только к подготовленному учебному mini-benchmark** и подтверждает корректность выбора модели для рассматриваемой предметной области. Он не означает универсальную точность модели на любых данных.

---

# Нормализация эмбеддингов

Эмбеддинги создаются с использованием параметра:

```python
normalize_embeddings=True
```

Нормализация позволяет корректно использовать cosine similarity без дополнительной обработки векторов.

---

# Батчинг

Для локального запуска используется размер батча:

```text
batch_size = 32
```

Такой размер соответствует рекомендациям для CPU и обеспечивает хорошее соотношение скорости обработки и потребления памяти.

---

# Кеширование

Для повторных запросов используется библиотека `diskcache`.

Ключ кеша содержит:

- имя embedding-модели;
- тип данных (`query` или `document`);
- исходный текст.

Такой подход гарантирует, что эмбеддинги разных моделей не будут смешиваться.

Проверка показала, что после повторного запуска приложения эмбеддинги успешно считываются с диска без повторного вычисления.

---

# Оценка стоимости индексации

Используется локальная embedding-модель, поэтому стоимость обращения к внешнему API составляет:

```text
0 ₽
```

### Пример расчёта

Предположим:

- 50 документов;
- каждый документ разбивается примерно на 10 фрагментов.

Всего:

```text
500 фрагментов
```

Каждый embedding содержит:

- 384 значения;
- тип `float32`;
- одно значение занимает 4 байта.

Общий объём векторов:

```text
500 × 384 × 4 = 768 000 байт
```

или примерно

```text
0.73 МБ
```

без учёта служебных структур и метаданных.

Если количество документов увеличить до 100, а каждый документ разбивать на 20 фрагментов, получится:

```text
2 000 × 384 × 4 = 3 072 000 байт
```

или примерно

```text
2.93 МБ
```

Даже такой объём остаётся небольшим и легко помещается в память современных векторных баз данных.

# Вывод

Для учебного RAG-проекта модель **intfloat/multilingual-e5-small** является удачным выбором, поскольку:

- поддерживает русский язык;
- оптимизирована для сценария «запрос → документ»;
- имеет компактную размерность (384);
- работает полностью локально;
- не требует оплаты внешнего API;
- показала корректное ранжирование во всех 6 сценариях подготовленного mini-benchmark;
- легко масштабируется на сотни и тысячи документов.
